## 为什么有这个仓库

GitHub 仓库同步是通过 [PR #1130](https://github.com/yetone/magpie/pull/1130) 进入 Magpie 的，作者即本仓库作者。该 PR 合并后，其中列出的一些后续工作没有继续推进，本仓库以插件形式承接这些工作。

| UTC | 事件 |
| --- | --- |
| 2026-10-07 08:30 | 打开 PR #1130，把 GitHub 作为 WebDAV、S3 之外的第三种同步后端 |
| 2026-10-13 07:28 | 合并进 main，并加入拒绝公开仓库的检查 |
| 2026-10-13 07:39 | PR 中列出后续清单：用量打包为一次上传；首次上传期间的进度反馈 |

本仓库不重写 Magpie：通过官方插件宿主，把同一套加密同步接到 GitHub 上，并完成上述后续工作。

## 与原生后端的区别

原生后端是 Magpie 设置里"同步到 GitHub"的一个选项；本插件在同步页仍是 **WebDAV**，中间隔着只监听 `127.0.0.1` 的本地桥接服务。加密、合并、恢复、撤销、用量共享仍由 Magpie 自己处理，插件只把文件操作翻译成 GitHub API 请求。

| 能力 | 原生后端 | 本插件 |
| --- | --- | --- |
| 交付方式 | 随 Magpie 发版 | 插件：发现页安装或 `magpie plugin add`，可独立升级，不必等 Magpie 发版 |
| 同步页显示 | 原生 GitHub 选项 | 仍是 WebDAV，地址由插件页生成 |
| 一轮 90 天日用量 | 一天一个文件，**一次提交一个文件** | Git Data API 批量写入，**一轮只生成 1 次提交** |
| 首次上传用量的反馈 | 可能长时间卡住，界面无提示 | 页面显示"正在暂存加密文件 / 正在提交到 GitHub"，并列出待提交文件数与下次重试时间 |
| 上传中断、重启、响应丢失 | 没有本地记录，未提交内容要等 Magpie 下次重传 | 本地日志 + 加密副本，重启后续传；响应丢失不会重复提交 |
| 同一用量文件被别的电脑改过 | 返回错误，不指明是哪个文件 | 逐文件标出冲突，可导出本地加密副本或采用远端版本（本地留档） |
| 待提交期间令牌过期 | 未提交内容没有本地副本，容易跟着一起丢 | 保留加密内容，同仓库换新令牌后继续提交 |
| 用量目录超过 1,000 条 | 报错，无法继续 | 改用固定提交版本的 Git Trees API 读取，不静默截断 |
| 状态与诊断 | 同步行上的一行错误 | 读、写权限分别验证，加上最近提交、下次重试和错误码提示，重启后仍在 |
| 限流 | 同步退避 | 冷却期内连保存配置和手动重试一起拒绝，并给出可重试时间 |
| 公开仓库 | 直接拒绝写入 | 不强制，但强烈建议私有（见[取舍](#取舍)） |
| 界面语言 | 跟随 Magpie 语言 | 插件页自带 **中文 / English** 切换，跟随浏览器语言并记住选择 |

## 安装

在 Magpie 的 **设置 → 插件 → 发现 → 非官方插件 · GitHub** 中搜索并安装 `magpie-github-sync-plugin`。仓库已添加 `magpie-plugin` 主题标签；能否在发现页中看到它，取决于 GitHub 搜索索引和 Magpie 缓存。较新版本约每十分钟刷新一次，旧版本可能缓存六小时。

也可以直接从 GitHub 仓库安装：

```sh
magpie plugin add github:bingqilinweimaotai/magpie-github-sync-plugin
```

安装后打开 **设置 → 插件**，让 Magpie 加载插件，并保持 Magpie 应用、`magpie web` 或网关运行。插件使用 Magpie 自带的 Bun 宿主，无需单独安装 Node.js、构建项目或运行安装脚本，也无需发布到 npm。

## 配置仓库

1. 保持 Magpie 运行，在浏览器中打开 [http://127.0.0.1:3437/](http://127.0.0.1:3437/)。
2. 填写已有的 GitHub 仓库（`owner/repo`），按需填写分支和文件夹，并提供对该仓库拥有 **Contents: read and write** 权限的 GitHub Token。建议使用私有仓库存放备份，然后保存配置。
3. 页面会生成本地桥接服务的地址（**Address**）、用户名（**User name**）和本地密码（**Local password**）。将它们填入 Magpie 的 **设置 → 同步 → WebDAV**。
4. 设置加密口令，选好需要同步的内容并保存。加密口令应与 GitHub Token 和本地密码不同。

配置页右上角可切换 **中文 / English**。首次打开时跟随浏览器语言，之后会在当前浏览器中记住选择；切换语言不会清空正在填写的内容。

保存前，插件会检查仓库和分支是否可访问；该检查无法保证分支保护规则允许写入。后续同步中的 GitHub 错误会显示在配置页面上。

备份保存在 `<folder>/magpie/magpie.magpie-backup`。可选的加密用量和配额文件保存在 `<folder>/magpie/usage/`；开启用量同步后，Magpie 首轮上传最近 90 天，之后只传昨天和今天，超过 90 天的由写入它的那台电脑删除。设置备份、配额历史与过期文件清理仍各自单独提交，内容未变化时不会生成提交。

**90 天之前的用量不会上传，这是 Magpie 自己的规则**（`usage.SharedDays = 90`），插件原样传达。共享的用量只用来在 Usage 页看最近三个月的跨电脑统计，不是长期归档；更早的记录仍留在本机的用量账本里，只是不进 GitHub 仓库。同样的 90 天窗口也决定了读取：超过 90 天的远端用量文件会被它的写入者删除，其他电脑也不会再合并它们。

如果仓库为空，首次备份会初始化默认分支；选择其他分支时，该分支必须已经存在。

## 后续维护的功能

以下各项为原生后端未提供，或提供方式不同的能力。

### 日用量打包成一次提交

Magpie 上传用量时是一天一个文件地 `PUT`。原生后端每个文件一次提交；本插件先把加密内容 `POST /git/blobs` 存成 blob，再把文件名和版本记进本地日志，等 Magpie 上传完去读用量目录（`PROPFIND`）时，**用一个 commit 把整批写完**：

- 一轮 90 天补传：90 个文件 → **1 次提交**。
- 暂存时不逐个等 GitHub：Git 用内容哈希命名 blob，所以上传前就知道返回的 SHA。插件把文件写进本地副本、记好日志就先答复 Magpie，真正上传在后台按最多 6 个并发排队进行。首次 90 天补传因此按磁盘速度跑完，而不是每等一天一次往返。
- 提交以最新的分支目录树为基底（`base_tree`）并做普通快进更新（`force: false`），**不会冲掉其他电脑的修改，也不会重写已有历史**。
- 提交前逐文件核对远端版本是否仍是上传时的基准；被别的电脑动过的文件单独标为冲突，其余文件照常提交。
- 分支在竞争中被推进时最多重试 3 次，仍失败则保留待提交记录并报"GitHub 分支持续变化"。

### 待提交日志、加密副本与断点恢复

每次暂存都会把加密内容复制到本地 `github-sync-plugin/usage-blobs/<blob SHA>`，并把清单写进 `github-sync-plugin/usage-pending.json`（只记文件名、版本和大小，**不记令牌**）。因此：

- **Magpie 退出、桥接服务重启、宿主被抢占**：重启后从本地加密副本恢复未完成的批次，重新确认 blob 后提交，完成后清理副本。
- **提交失败**（令牌过期、分支保护、限流、网络中断）：日志保留，页面显示待提交文件数和下次重试时间，不会因为一次失败就丢掉这批上传。
- **响应丢失**：发布过程中连接断开后重试，会先发现"远端已是这个版本"，于是**不再生成第二次提交**。
- **同一文件反复上传**：同批次内只保留最后一次内容，但基准仍是最初那次远端版本，避免自己和自己冲突。
- **空闲或关闭时也会提交**：连续空闲 15 秒、或桥接服务正常关闭（包括 Magpie 退出、插件被禁用的平滑收尾）时补提交，不必等 Magpie 的下一次同步。

### 冲突：先看得见，再决定怎么办

用量文件冲突不只是一个 412 错误：

- 配置页列出冲突文件名，并保留本地加密副本；
- **导出加密副本**：下载本地那份 `.magpie-usage` 密文——下载的就是密文，插件从不接触明文；
- **采用远端版本**：本地密文先归档到 `github-sync-plugin/usage-archive.json` 与 `usage-blobs/`，然后解除该文件对后续同步的阻塞；
- 归档索引写在删除日志之前，所以中途断电也不会两边都没有；
- 归档只留在本机，**不会上传到 GitHub**。

### 令牌过期时不必先清空待提交

换 Token 时最怕连待提交内容一起重来。这里保存配置会先尝试发布待提交批次；如果旧令牌被拒（401），仍然允许你为**同一个仓库**保存新 Token，待提交的加密内容原样保留并用新令牌重试。只有切换仓库、分支或文件夹时才要求先发布，避免把内容写进别的地方。

### 同步状态与读写诊断

配置页的"03 — 同步状态"里能看到：

- **最近成功操作**与**最近 GitHub 提交**（提交时间取自 GitHub 的提交历史，不是本机时钟）；
- **待提交文件数**与**下次自动重试时间**；待提交文件在上传过程中显示为「已接收 / 总数」，`3 / 90` 这样的数字让一次长补传看起来在动，而不是卡住；
- **仓库读取权限**与**仓库写入权限**分别显示"已验证 / 尚未验证 / 失败"。保存配置只证明读得到；只有本机用当前令牌真正提交成功过，写入才会"已验证"。别的电脑、别的令牌留下的提交不会让这里变绿；
- 当前动作（空闲 / 正在读取远端文件 / 正在暂存加密文件 / 正在提交到 GitHub / 正在检查仓库 / 正在归档冲突副本 / 正在清理过期文件），每 5 秒刷新一次，后台标签页不轮询。

这些状态写在 `state.json` 的 `syncStatus` 里，**桥接服务重启后仍然保留**；换令牌或换仓库时写入验证自动失效，避免沿用旧结论。错误码会带出对应建议：令牌失效、权限不足、分支规则拒绝写入、GitHub 限流、仓库或分支找不到、用量文件冲突。

### 限流冷却

GitHub 的 429 或 403 限流响应会带着 `Retry-After` / `X-RateLimit-Reset` 一起传回，插件据此进入冷却：冷却期内保存配置、手动重试、自动重试一律拒绝并给出剩余秒数，**不浪费配额去打已知会被拒的请求**。自动重试的等待区间为 60 秒到 6 小时。

### 超过 1,000 条的用量目录

GitHub Contents API 的目录列表到 1,000 条就不再返回更多，原生后端到点直接报错。本插件在列表长度达到 1,000 时改走 Git Trees API：以**固定提交版本**读取目录树，逐级下钻到 `magpie/usage`，并要求 `truncated: false`、每个条目都是合法的 blob 与 SHA——**宁可明确报错，也不静默给一份截断的列表**。截断的列表会让 Magpie 以为别处的用量文件凭空消失了。

### 目录快照复用

日用量上传是密集的小请求，每次都重读仓库和目录会很慢。插件在一次会话内复用目录快照：日用量文件的读取、版本检查和内容未变化的重复上传直接命中快照；出现目录操作（发布、删除、列目录）或快照超过 15 秒后才刷新；发布时仍以最新分支核对版本，快照只省读请求，不放松冲突检查。测试里 90 个文件的读取、`HEAD` 和重复上传合计只用了 94 次 GitHub 请求。

### 上传前先校验封装格式

桥接服务只接受 Magpie 自己封装的密文，而且**按路径校验封装类型**：设置备份必须是 `magpie-backup` 封装，用量与配额历史必须是 `magpie-data` 封装，版本为 1、`pbkdf2-sha256`、600,000 次迭代，单个文件最大 64 MiB。明文、伪造的 JSON、版本号不对的封装都会在上传前被拒绝，**一个 GitHub 写请求都不会发出**。

### 配置差异

配置页的"04 — 同步会改动什么"把**本机配置**和**服务器上那份备份**摆在一起，回答"这次同步会动什么"。

界面上用的是 **Magpie 同步页自己的叫法**——供应商、设置、Profile、agent 的模型、资源库——熟悉 Magpie 的人可以直接对上。

比较的粒度对齐 Magpie 的 `hashes()`（`internal/davsync/davsync.go`），它把配置分成 5 个部分，每个部分包含的并不止一个文件：

| 部分 | 展开为 |
| --- | --- |
| 供应商 | 供应商本身、**路由组**（含选择策略与成员顺序）、供应商顺序、路由组顺序、网页搜索 API、供应商图标、**插件** |
| 设置 | 一般设置，以及**网关密钥** |
| Profile | 各配置档案的字段 |
| agent 的模型 | 按 Magpie 自己的部分 hash 判断，不逐字段比较 |
| 资源库 | 指令、MCP 服务器，以及逐个 skill（新增、删除、内容改动） |

**资源库**：本机 `library.json` 为每个 skill 保存文件夹的 hash，备份中保存的是内联的 `files`（base64 全文）。插件按 Magpie `hashWalk`（`internal/library/skillcheck.go`）的同一规则——按路径排序，每个文件写 `file <路径> <大小>\n` 再附内容，跳过 `.git` 与 `.magpie-library`——把备份里的 `files` 算出 hash，与本机保存的 hash 比对。

**agent 的模型**：这部分是 Magpie 对各 agent 实时配置的快照，值来自每个 agent 自己的配置文件（codex 的 `config.toml`、Claude 的 `settings.json` 等）。插件不重做各 agent 的解析规则，因此只比较 Magpie 自己的部分 hash，页面上标注"按 magpie 自己的 hash 比对"：一致表示上次同步把这一部分整体搬过，而不是每个模型都逐项核对过。

比较时遵循的规则：

- 只属于本机的设置（窗口大小、代理、端口、托盘等，即 Magpie 的 `KeepOwn`）不参与比较，每台电脑各自保留；
- 路由组的选择策略缺省为"智能"，因此未写入与该值等价；
- 备份不带密钥时（同步时未勾选），本机一侧先去密钥再比，密钥不算差异；
- 比较使用上次同步留在本机的备份副本，不额外请求 GitHub，不消耗配额；代价是它反映的是上次同步时的服务器状态，其他电脑此后推送的内容要等下次同步才可见。

**凭据一律打码**：任何名字像 `key`、`token`、`secret`、`password`、`authorization`、`cookie` 的字段都只显示 `••••` 加末四位，无论它出现在条目里还是嵌套在 `headers` 中。这样能看出"是哪个 key 变了"，但拿不到值。

**比较需要显式授权**。默认关闭：点"允许在此页面比较"之前，`/api/diff` 直接返回 403。开启后这个选择记在 `state.json` 的 `plaintext` 里，桥接服务重启后仍然有效，随时可点"停止比较"撤销。

授权之后，桥接服务才会读 `sync.json` 里的加密口令，在**本地进程内**打开备份。口令和配置明文都不会送到浏览器——页面收到的只有差异条目，且其中的凭据已经打码。这也是插件唯一会接触加密口令的地方，不用时请关掉。

## 在另一台电脑上恢复

在另一台电脑上安装插件，绑定 **相同的仓库、分支和文件夹**，再使用这台电脑生成的桥接凭据配置 WebDAV。在 Magpie 中使用 **相同的加密口令和同步内容选项**，点击 **恢复（Restore）** 即可。Magpie 会保留被替换的本地配置，供 **撤销（Undo）** 使用。自动同步和手动同步均通过 Magpie 原有的操作入口完成。

不同电脑的本地密码可以不同，插件不会接收加密口令。哪些供应商、密钥、设置、配置档案、Agent 模型和资料库数据可以迁移，由 Magpie 的备份规则决定；同步范围不包括克隆工作目录或复制电脑上的所有本地文件。

## 换用 Magpie 自带的 GitHub 同步

插件与 Magpie 自带的 GitHub 同步使用同一套目录布局：设置备份在 `<folder>/magpie/magpie.magpie-backup`，用量和配额在 `<folder>/magpie/usage/`。所以两边可以随时互换，已经上传的备份不需要迁移或转换。

换用时在 **设置 → 同步** 里选择 GitHub，填 `github://owner/repo/<folder>`、相同的分支和相同的 Token，加密口令保持不变，自带后端就能直接读到插件上传的内容。反过来也一样：关掉自带后端，重新在插件页面绑定同一个仓库、分支和文件夹，再把生成的地址填回 WebDAV。

换到自带后端之后，插件独有的那些行为就不再生效——一轮 90 天用量会回到 90 次提交，用量上传中断没有本地副本可续，冲突只剩一行错误，配置页也不再显示同步状态。想拿回这些行为，换回插件即可。

## 兼容性与运行方式

- 插件通过 WebDAV 桥接，同步页面中仍显示为 WebDAV，不会新增原生同步后端选项。由于插件页面没有独立的后台服务分类，它可能将此插件标为供应商；插件本身不会添加模型或虚拟供应商账号。
- 插件初始化时会启动桥接服务。原生同步 API 不会自行初始化插件；如果仅通过 CLI 同步时提示连接被拒绝，请先打开插件页面。
- 同一配置档案下的多个 Magpie 或 CLI 宿主会共享桥接服务。持有服务的宿主退出后，其他宿主会在约两秒内接管；在此期间发起的同步可能需要重试。
- 禁用或移除插件后，监听服务会在约两秒内关闭，已开始的操作会执行完毕（待提交的用量批次会在这段收尾里发布）。原有同步设置会保留；如果不再使用同步，还需关闭 WebDAV 同步。
- 不同配置档案需要使用不同端口。可运行 `magpie plugin options magpie-github-sync-plugin '{"port":3438}'`，然后访问 `http://127.0.0.1:3438/`。在 PowerShell 中，将 JSON 作为一个用单引号包裹的参数传入。
- 修改仓库、分支或文件夹后，生成的 WebDAV 地址也会变化，需要更新 Magpie 同步页面中的地址。旧地址会报错，以免意外访问其他仓库。
- WebDAV 与 S3 之间的切换沿用 Magpie 原有实现；插件不会添加原生 GitHub 同步的三后端配置选择器。

### 取舍

- **私有仓库**：原生后端会直接拒绝公开仓库，插件不强制，只在配置页和本文件里建议。密文放在公开仓库里，任何人拿到全部历史后可以离线试口令——请务必用私有仓库。
- **提交粒度**：日用量走批量提交；设置备份、配额历史、删除过期文件仍是一次操作一次提交。批量的意义是压缩密集的小文件，而不是把不同性质的操作混在一起。
- **`usage-pending.json` 属于本机**：它记录的是"这台电脑还没交出去的东西"，不随备份同步；换电脑或删配置目录前，确认里面没有待提交文件。

## 凭据与错误处理

配置和独立的本地桥接密码保存在 `<magpie-config>/github-sync-plugin/state.json`。在 POSIX 系统上，该文件权限为 `0600`；在 Windows 上，继承用户配置目录的访问控制权限（ACL）。该文件不包含在远程加密备份中，每台电脑都需要单独配置凭据。同步状态、待提交日志和加密副本也放在同一个 `github-sync-plugin/` 目录下，权限相同，同样不上传。

GitHub Token 只会发送到 `https://api.github.com`，插件拒绝重定向。仅在仓库未改变时，将 Token 留空才会复用已保存的 Token；已保存的 Token 不会回填到配置表单。设置页请求需要同源 CSRF Token 和 loopback Host / Origin 校验，WebDAV 访问需要本地桥接密码（常量时间比较）。

写入时通过 blob SHA 检查文件版本。如果另一台电脑已修改备份，插件会返回前置条件失败，让 Magpie 重新读取并合并。仓库或分支不存在、元数据格式错误、读取失败和认证失败都会明确报错，不会被当作备份不存在处理。GitHub 限流信息会传回 Magpie，由其同步退避机制处理。仓库提交历史会保留之前的加密版本。

## 开发与测试

插件没有运行时依赖（在 Magpie 的 Bun 宿主里运行 ESM，测试用 Node.js 20+）：

```sh
npm test
```

38 个测试（35 个默认运行，3 个集成测试需要下面的环境变量才会执行），覆盖仓库与分支校验、条件写入、封装格式、限流冷却、令牌替换、冲突处理与归档、批量提交与快照复用、发布失败后的日志恢复、响应丢失的幂等、空闲与关闭时的补提交，以及状态持久化。测试使用临时配置档案、真实的本地 HTTP 请求和内存中的模拟 GitHub API（同时校验请求只会发往 `api.github.com`、且必须禁止重定向），不会读写用户的 Magpie 配置。CI 会在 Windows、Linux 和 macOS 上运行测试套件。

可选集成测试通过 `BUN_BIN` 和 `MAGPIE_HOST` 指定 Bun 与 Magpie 的 `internal/plugin/host.js`，通过 `MAGPIE_BIN` 指定 Magpie 可执行文件。测试会验证宿主接管和插件禁用，以及使用模拟 GitHub 服务进行原生加密上传、内容未变化时的同步、新配置档案中的恢复与撤销；开启用量同步时，还会验证 90 天用量合并为一次提交、配额的加密上传、跨配置档案下载合并及内容未变化时不新增提交。用量错误会单独检查同步状态，因为这类错误不会让 CLI 命令失败。测试配置档案均与用户文件隔离。
